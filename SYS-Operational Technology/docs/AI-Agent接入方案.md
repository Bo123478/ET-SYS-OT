---

## 0. 文档说明

本方案面向“下一阶段数字化平台”的 AI-Agent 能力建设，重点解决以下业务问题：

1. 现场设备和系统日志杂乱、量大、异构，运维人员难以快速定位问题；
2. 图片和屏幕截图信息难以自动提取有效特征；
3. 历史案例、知识库与故障处理经验缺少统一检索与复用；
4. 业务人员需要“建议方案”而不是“直接越权执行”，以确保安全和可审计。

AI-Agent 在本项目中的定位是：

- 作为“智能分析与决策支持”能力层；
- 负责日志分析、图片识别、案例检索、故障归因建议、决策辅助；
- 通过与 Dataverse / SharePoint / Teams / Power Automate 协同，实现闭环式协助；
- 绝不代替人类对配置、权限、系统状态、关键业务操作进行直接执行。

本文档与 Phase 1 的工程治理文档保持一致：

- 角色边界保持清晰；
- 数据与权限保持受控；
- AI 只负责分析与建议，不越权改动核心配置和代码；
- 所有结论必须留痕、可追溯、可复核。

## 1. 目标与定位

### 1.1 业务目标

AI-Agent 的核心目标是在运维数字化平台中建立“观察 → 分析 → 建议 → 审批 → 执行”的智能闭环，降低人工排障成本、提升故障识别速度，并为现场人员提供结构化决策建议。

目标包括：

- 日志文本快速聚类和归因；
- 现场图片与设备截图识别辅助；
- 历史案例与知识库统一检索；
- 重要问题给出结构化建议方案；
- 关键动作仍由人工确认后执行。

### 1.2 认知边界

AI-Agent 不等于“代码生成助手”或“自动改动核心系统的代理”。

在本项目中，它的工作边界是：

| 能力 | 是否允许 | 说明 |
|---|---|---|
| 日志摘要 | ✅ | 将大量日志整理成结构化问题描述 |
| 图片/截图识别 | ✅ | 识别设备状态、告警区域、界面异常 |
| 案例检索 | ✅ | 检索历史问题和已解决方案 |
| 方案建议 | ✅ | 给出修复方向、优先级、风险提示 |
| 自动改代码 | ❌ | 不允许直接改动项目源代码 |
| 自动改配置 | ❌ | 不允许直接改 Dataverse / Flow / SharePoint 配置 |
| 自动执行运维动作 | ❌ | 仅允许在审批后由人工或标准流程触发 |
| 直接访问高权限资源 | ⚠️ 受控访问 | 仅在明确授权和最小权限条件下进行只读分析 |

### 1.3 与项目既有治理的关系

AI-Agent 是平台增强层，不是第三个开发角色，也不是对 A/B 角色的绕过。它遵循现有治理原则：

- A/B 分工继续保持；
- 配置与代码变更仍需受现有规则约束；
- AI 产生的结论只作为建议输入；
- 所有行为都应被记录在审计日志中。

## 3. AI-Agent 能力设计

### 3.1 日志分析

日志分析能力用于解析现场设备、应用系统、网络和平台层日志，自动识别：

- 异常类型；
- 时间窗口；
- 系统组件；
- 错误模式；
- 相关联系人和受影响对象。

典型输入：

- .log、.txt、.csv、JSON 文件；
- Power Automate 运行记录；
- Dataverse 审计日志；
- 应用与系统输出日志。

输出：

- 问题摘要；
- 可能根因列表；
- 风险级别；
- 建议的下一步检查项。

### 3.2 图片与证据识别

图片识别能力允许处理：

- 现场设备照片；
- 截图；
- 监控画面；
- 报警屏幕快照。

可以识别：

- 设备状态（正常/告警/故障）；
- 指示灯状态；
- 报警区域；
- UI 异常元素；
- 参数和界面标签。

但所有识别结果都必须与业务现场信息相结合，不能直接作为“最终结论”直接执行处置。

### 3.3 历史案例检索

AI-Agent 需要连接项目历史信息，如：

- 已结案工单；
- 故障案例库；
- 知识库手册；
- 变更记录；
- 设备配置基线。

通过检索，不仅能快速提示“相似案例”，还能为运维人员提供：

- 过去的处理顺序；
- 影响范围；
- 处理时长；
- 复现条件；
- 回避事项。

### 3.4 方案建议输出

AI-Agent 输出的建议需要具备结构化格式，避免模糊结论。建议模板如下：

| 字段 | 示例 |
|---|---|
| 事件摘要 | 设备 A 采集异常，日志显示网络超时 |
| 可能根因 | 交换机端口故障、配置漂移、网络抖动 |
| 证据支持 | 日志时间窗口、截图中指示灯异常 |
| 建议步骤 | 检查接口状态、比对配置、验证链路 |
| 风险提示 | 若误判，可能导致误停机 |
| 置信度 | High / Medium / Low |
| 需要人工确认 | 是 |

## 4. 实现方法

### 4.1 分层实现方法

AI-Agent 的落地方式建议采用“分层能力 + 受控接入”的方式，而不是“一次性整合全部功能”。

#### 第一层：数据收敛与标准化

- 对 Dataverse、SharePoint、Teams、日志文件统一归档；
- 将问题对象统一成标准结构：Issue ID、设备、时间、应用、证据、状态、权限级别；
- 对敏感字段做脱敏和访问控制。

#### 第二层：分析引擎

- 日志分析采用文本分类 + 规则过滤 + 大模型推理组合模式；
- 图片识别采用 OCR + 视觉模型 + 业务规则比对；
- 经验库检索采用语义搜索和候选案例匹配。

#### 第三层：决策建议

- AI 生成结构化诊断建议；
- 输出置信度与证据链；
- 对高风险动作触发人工二次确认。

#### 第四层：审批与执行

- 只有人工确认后，才允许进入标准工作流；
- 执行动作通过 Power Automate 或现有运维流程触发；
- 关键操作必须留下审批记录和执行时序。

### 4.2 推荐技术落地方式

结合当前项目的 Microsoft 生态，推荐采用如下组合：

| 能力 | 推荐方案 |
|---|---|
| 语言模型 | Azure OpenAI / 自定义托管模型 |
| 图像识别 | Azure AI Vision / OCR / 计算机视觉能力 |
| 文档检索 | Azure AI Search 或企业知识库索引 |
| 数据管理 | Dataverse + SharePoint + Azure Blob |
| 流程集成 | Power Automate + Teams |
| 审计 | Dataverse 审计 / SharePoint 审计 / 日志追踪 |
| 安全 | Entra ID、最小权限、Key Vault、网络隔离 |

### 4.3 典型工作流

#### 场景 A：日志异常分析

1. 用户上传日志包或问题工单；
2. 系统拉取相关日志和设备历史记录；
3. AI 对日志进行结构化聚类；
4. 生成诊断摘要和可能根因；
5. 检索相似历史案例；
6. 返回建议方案给运维人员；
7. 人工确认后进入修复或升级流程。

#### 场景 B：图片问题识别

1. 用户上传现场图片或屏幕截图；
2. AI 检测设备状态、告警区域、UI 异常；
3. 对照知识库和历史案例；
4. 给出风险评估和建议检查重点；
5. 由现场工程师人工验证并执行。

#### 场景 C：案例推荐

1. 用户提交问题对象；
2. AI 搜索历史案例、手册和同类问题；
3. 返回相似案例、相似症状、历史修复手段；
4. 人工判定是否套用该方案。

## 5. 安全与治理要求

### 5.1 访问控制

AI-Agent 对外部资源必须遵循“最小权限原则”：

- 只读访问优先；
- 对敏感日志和证据数据做脱敏；
- 仅在授权范围内访问；
- 高权限工单需经审批后再开放。

### 5.2 岗位边界

AI-Agent 不得替代以下职责：

- 业务数据配置审批；
- 安全策略变更；
- 生产环境关键操作；
- 代码提交与源代码变更；
- 权限分配与角色变更。

AI 的输出仅作为建议，不得直接改动系统运行状态。

### 5.3 审计与留痕

所有 AI 请求与输出必须记录：

- 请求时间；
- 请求来源；
- 涉及对象；
- 输入内容摘要；
- 模型输出概要；
- 人工审批人员；
- 最终执行动作与结果。

### 5.4 风险控制

超过以下任一条件的场景，必须触发人工二次确认：

- 影响生产环境；
- 可能导致停机或重大业务影响；
- 涉及安全、权限、配置改动；
- 置信度低且结论存在不确定性。

## 6. 实施路线

### 6.1 阶段 1：MVP 能力（先做“低风险、高价值”）

- 日志摘要与问题分类；
- 图片/截图识别；
- 历史案例检索；
- 方案建议输出；
- 审批和审计留痕。

### 6.2 阶段 2：集成化平台化

- 与 Dataverse Issue / Evidence / History 等对象打通；
- 与 Teams 和 Power Automate 集成；
- 支持自动生成建议卡片；
- 支持针对工单的嵌入式 AI 助手。

### 6.3 阶段 3：智能闭环

- 支持提升提案、故障重演、优先级推荐；
- 支持基于历史案例的标准处置建议；
- 支持分析结果回流到知识库和规程文档。

---

## 7. 成功判定标准

AI-Agent 接入成功的判定标准包括：

1. 工程师能更快识别故障类型和根因范围；
2. 现场图片和日志能被自动结构化分析；
3. 历史案例能被快速检索并输出可执行建议；
4. 人工审批流程清晰且可审计；
5. 不发生越权操作与安全事故；
6. AI 输出对人类决策具有真实帮助，而不是“只打字不做判断”。

---

## 8. 关键风险与应对

| 风险 | 表现 | 应对方案 |
|---|---|---|
| 误判 | AI 给出错误根因或误导建议 | 通过置信度、证据链、人工复核降低风险 |
| 权限滥用 | AI 访问超出最小范围 | 完成最小权限设计与审批门禁 |
| 数据泄露 | 日志、图片或敏感信息被错误暴露 | 脱敏、权限控制和日志审计 |
| 方案漂移 | AI 建议与业务流程脱节 | 方案需绑定知识库和标准工单模板 |
| 人工依赖过高 | AI 不起作用 | 先做高价值、低风险场景，逐步扩展 |

---

## 9. 结论

AI-Agent 不是让系统“自动替人处理所有问题”，而是让平台具备更强的观察力、理解力和建议能力：

- 看懂日志；
- 识别图片；
- 检索历史案例；
- 提供修复建议；
- 让人类在安全、可控、可审计的前提下进行最终决策与执行。

这与当前项目的治理原则完全一致：

- AI 是辅助能力，不是越权执行者；
- 人类仍是最终决策者和责任人；
- 平台整体仍然保持可控、可审计、可演进。

因此，本方案可作为项目从“数字化运维协同平台”迈向“智能分析与决策支持平台”的工程基线，用于后续 Phase 2 与 Phase 3 的实施落地。
