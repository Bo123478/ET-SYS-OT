## 1. 入口策略总览

| 阶段 | 入口 | 定位 | 状态 |
|---|---|---|---|
| **1a** | Microsoft Forms | **临时快速通道** | 立即上线 |
| **1b** | Canvas App | **唯一正式入口** | 排期后补 |
| — | 系统内嵌 / 日志工具 | Phase 3 预留 | 未开发 |

**策略逻辑**：用 Forms 快速验证流程闭环（Teams 通知、状态流转、证据上传是否真的能跑通），把工程重心放在 Dataverse 数据模型与 Power Automate 流程上。等闭环被验证、字段需求稳定后再投入 Canvas App，避免在需求未固化时先做 UI 导致返工。

## 2. Phase 1a — Microsoft Forms 入口

### 2.1 表单结构

表单名称：**《现场设备与系统运维问题反馈》**

分为 4 个分区，对应 `bjops_issue` 的 A/B/C 组字段。

### 2.3 流程自动填写的字段（用户不需填）

| 字段 | 来源 |
|---|---|
| `bjops_issuenumber` | 自动编号 |
| `bjops_status` | 默认 `New` |
| `bjops_source` | 固定 `Forms` |
| `bjops_formsresponseid` | 表单响应 ID（幂等键） |
| `bjops_productionline` | 从设备台账带出 |
| `bjops_sladeadline` / `bjops_resolutiondeadline` | FL-01 按 `slaconfig` 计算 |
| `bjops_correlationid` | FL-01 生成 |
| `bjops_automationupdate` | 默认 `否` |

### 2.4 下拉选项的维护方式

Forms 的下拉选项是**表单内静态定义**，无法从 Dataverse 动态加载。因此「所属应用」的选项需要：

| 步骤 | 操作 |
|---|---|
| 1 | 在 `bjops_application` 台账中维护应用清单 |
| 2 | **人工**把应用名称同步到 Forms 下拉选项 |
| 3 | 适配器流按**名称**匹配 `bjops_application` 记录 |

> ⚠️ **这是 Forms 的固有限制**：新增应用时必须两边都改，且**没有机制防止遗漏**。
> **缓解措施**：适配器流在匹配失败时**必须发告警**到 `03-Power Platform` 频道，而不是静默丢字段或建一条无应用的记录。这样至少能发现漂移。

### 2.5 文件上传的处理

Phase 1a 采用**两级策略**：

| 方案 | 说明 | 采用 |
|---|---|---|
| **A** | 使用 Forms 自带文件上传，将文件存入表单所有者的 OneDrive，适配器流再搬运到 SharePoint | ⚠️ 不推荐 |
| **B（推荐）** | 表单不收集文件，要求用户把图片发到 Teams 频道，由运维手工整理 | ✅ 采用 |

**选择 B 的理由**：

- Forms 的文件上传会把文件存到**表单创建者个人的 OneDrive**，而非团队位置。该账号一离职，文件即不可访问。
- 搬运到 SharePoint 需要额外的流，且 Forms 附件与响应的关联仅靠文件名，重名会串。
- 现场操作员本来就在 Teams 里，把图发到 `02-设备与客户端` 频道是更自然的操作。

**Phase 1b 改进**：Canvas App 直接上传到 SharePoint 文档库，彻底解决此问题。

### 2.6 校验策略（双层）

| 层 | 位置 | 目的 |
|---|---|---|
| 第 1 层 | **表单必填设置** | 提供即时反馈，减少无效提交 |
| 第 2 层 | **适配器流的条件判断** | 防止绕过表单直接调用 API；校验字段值合法性（如设备编码是否存在） |

**第 2 层的必要性**：Forms 的必填只约束 UI，不构成数据约束。且适配器流的映射逻辑会随着时间演进（新增字段、调整取值），第 1 层无法覆盖。

**第 2 层校验失败的处理**：

1. 仍然创建 Issue 记录（**避免丢单**），状态置为 `New`；
2. 在 `bjops_issuehistory` 中写一条 `changesource = 流程` 的记录，说明缺失项；
3. 发通知到 `03-Power Platform` 频道，附响应 ID 与缺失字段清单。

> **设计取舍**：校验失败时不阻断建单。理由是现场问题已经发生，因为表单填得不规范而拒绝受理，会导致用户绕过平台直接找运维——这恰恰是本项目要消除的行为。宁可建一条不完整的记录，也不能丢单。

### 2.7 表单生命周期与版本管理

| 事项 | 处理 |
|---|---|
| 表单所有权 | 用**共享邮箱或服务账号**创建，不可用个人账号 |
| 表单修改 | 修改前导出当前结构存档（Forms 无版本管理） |
| 表单停用 | 1b 上线后保留表单但改为「快速反馈」简版，或关闭 |

## 3. Phase 1a 已知技术债（必须承认）

> 以下限制不是"以后优化"，**是当前方案无法做到的事**。需在向业务方汇报时明确说明。

| # | 技术债 | 影响 |
|---|---|---|
| 1 | **Forms 表单定义不是解决方案组件** | 字段变更**无法被 Git 追踪**；无法随解决方案部署；三个环境的表单需人工分别核对 |
| 2 | **不支持条件显示逻辑** | 无法实现"选择问题类型 = Bug 时才显示复现步骤"；所有用户看到全部字段 |
| 3 | **不支持跨表查询/联动** | 选择设备后**无法自动带出**当前版本、生产线、负责人组——而这是设计稿 §8.4「版本自动识别」的核心需求 |
| 4 | **下拉选项需人工同步** | 台账新增应用后容易漏改表单，导致匹配失败（已加告警缓解） |
| 5 | **文件上传位置不可控** | 存入个人 OneDrive，已通过"不收集文件"规避 |
| 6 | **无法感知字段变更影响** | 表单改字段后，适配器流的映射必须人工同步修改，漏改会导致字段永久缺失且**不报错** |

**结论**：**1a 阶段必须显式标注 Forms 为临时通道**，在表单开头与提交成功页说明"正式入口上线后请改用"。

### 3.1 技术债 #6 的专项缓解

技术债 #6（字段变更不报错）是最危险的一项，因为它**静默失效**。缓解措施：

1. 适配器流的每个字段映射后加**空值检查**；
2. 建单后 FL-01 校验核心字段非空（§15.2 验收第 2 条），缺失则告警；
3. 1a 期间**冻结表单字段**——任何字段变更需走变更评审（哪怕只是改选项文案）。

## 4. Phase 1b — Canvas App 入口

### 4.1 屏幕设计

| 屏幕 | 名称 | 功能 |
|---|---|---|
| 1 | **提交问题** | 动态字段、设备/应用联动、版本自动带出、附件上传 |
| 2 | **详情与处理** | 状态流转、分派、历史时间线、证据与日志包管理 |
| 3 | **我的问题** | 按 `reporter` 过滤，展示自己提交的问题及状态 |

### 4.2 屏幕 1 — 提交问题

**相对 Forms 的改进点**

| 能力 | Forms | Canvas App |
|---|---|---|
| 选择应用后加载该应用的设备列表 | ❌ | ✅ |
| 选择设备后自动带出生产线 | ❌ | ✅ |
| 自动带出应用当前生产版本 | ❌ | ✅ |
| 按问题类型动态显示字段 | ❌ | ✅ |
| 直接上传到 SharePoint 文档库 | ❌ | ✅ |
| 提交前校验设备编码是否存在 | ❌ | ✅ |

**实现要点**

- 设备下拉：`Filter(bjops_equipment, bjops_application.bjops_applicationid = selectedApp)`。
- ⚠️ **委派警告**：上述 `Filter` 若涉及非委派列会静默只返回前 500 条。**开发期将应用设置中的「数据行限制」调为 1**，以便立即暴露委派问题。上线前再调回。
- 版本带出：`LookUp(bjops_application, ...)` 取 `bjops_currentprodversion`，并将 `versionsource` 置为「自动读取」。
- 附件：使用 SharePoint 连接器的 `Create file`，路径 `IssueEvidence/{yyyy}/{IssueID}/`。
  ⚠️ **先建 Issue 再传附件**——`{IssueID}` 依赖 Issue 编号，因此提交顺序是"建记录 → 取编号 → 传文件 → 回写 URL"。

### 4.3 屏幕 2 — 详情与处理

**功能**

| 区域 | 内容 |
|---|---|
| 头部 | 问题编号、标题、严重度、状态徽章 |
| 主体 | 问题描述各字段（只读/可编辑按角色） |
| 状态操作 | 状态流转按钮（按当前状态动态显示合法目标状态） |
| 分派 | 负责人选择器 |
| 时间线 | `bjops_issuehistory` 按 `changedon` 倒序 |
| 证据 | 图片缩略图网格 + 上传入口 |
| 日志包 | LogPackage 列表 + 上传入口 |

**实现要点**

- **状态流转按钮必须按状态机生成**，不能做成自由下拉。
  即：`bjops_status = Assigned` 时只显示「→ Analyzing」「→ WaitingForInfo」按钮。自由选择状态会让用户跳到非法状态，破坏 §11 状态机的完整性。
- 时间线用 `Gallery` + `Filter(bjops_issuehistory, bjops_issue.bjops_issueid = currentIssue)`，按 `changedon` 倒序。
  ⚠️ **委派注意**：`bjops_changedon` 排序是委派的；但如果用 `Filter` 后接 `Sort`，需确认 `Filter` 条件本身可委派，否则排序只作用于已获取的前 500 条。

### 4.4 屏幕 3 — 我的问题

- 数据源：`Filter(bjops_issue, bjops_reporter.email = User().Email)`。
  ⚠️ **委派注意**：多态查找列的 `.email` 展开**不可委派**。改用预置的 `bjops_reporteremail` 文本列（已在数据字典中为此目的定义）。
- 展示：编号、标题、状态、提交时间、最后更新。
- 点击进入屏幕 2。

### 4.5 Teams 深链

卡片中的「查看详情」按钮使用：

```text
{PortalUrl}/main.aspx?appid={CanvasAppId}&pagetype=entityrecord&etn=bjops_issue&id={IssueGUID}
```

或 Canvas App 专用深链格式。`PortalUrl` 来自环境变量，不硬编码。

## 6. 1a → 1b 收敛路径

| 阶段 | 动作 |
|---|---|
| **1b 上线前** | 冻结 Forms 字段（技术债 #6 的缓解措施） |
| **1b 上线时** | Canvas App 设为唯一正式入口；Forms 改为「快速反馈」简版（仅标题 + 描述 + 邮箱），由运维补全字段 |
| **1b 上线后 1 个月** | 统计 Forms 与 Canvas App 的提交比例，评估是否关闭 Forms |
| **关闭条件** | Forms 提交量连续两周 < 总提交量的 5% |

> 不建议**立即**关闭 Forms。现场操作员已养成习惯，突然关闭会产生阻力，反而促使用户绕过平台。应允许并行一段时间，用体验差异自然迁移。
