# 无代码（手工配置）实施方案

> 本目录是一套**与 [`../docs/`](../docs/) 并列的备选实施方案**，不替代旧方案，供对比后再选。

## 这套方案是什么

**全部通过浏览器门户界面完成**——登录门户、点菜单、填表单、向导式配置。不使用任何本地工具链、命令行、脚本或 CI/CD 流水线。

交付形态是**方案文档 + 逐步操作手册**：每本手册写到「点哪个菜单、填什么值、期望看到什么结果」的粒度，照着手册即可独立完成配置。

## 与旧方案（`../docs/`）的根本差别

两套方案**业务模型完全相同**（同样的表、同样的字段、同样的状态机、同样的流程），差别只在**实施与运维手段**：

| 维度 | 旧方案（`../docs/`）代码化 | 本方案（无代码） |
|---|---|---|
| **唯一源头** | **Git 仓库**。DEV 环境是部署产物 | **DEV 环境本身**。仓库里没有源码 |
| 表/列/关系定义在哪 | `.cdsproj` 解决方案源码（可 diff、可评审） | DEV 环境的 Dataverse（点界面维护） |
| 变更历史 | Git commit 历史，逐行可追溯 | 无。只能靠 Dataverse 审计 + 解决方案 `See history` |
| 代码评审 | 有 PR 评审 | 无。只能靠**发布前截图 + 双人核对** |
| 发布方式 | GitHub Actions 自动跑 `pac solution import` | 手工导出 zip → 手工导入，或 Pipelines 点几下发布 |
| 回滚能力 | `git revert` + 重新部署，可精确回退到任意提交 | **做不到精确回退**。托管解决方案升级不会删除旧组件 |
| 环境变量注入 | 按环境提交 `DeploymentSettings/<env>.json` | 在导入向导里逐个填值（向导会提示） |
| 连接授权 | 导入时审批 + 服务主体 | 在导入向导里手工重新授权 |
| 所需许可 | Power Apps 每用户计划 + GitHub（免费额度够） | Power Apps 每用户计划；若要 Pipelines 则需**托管环境（premium）** |
| 所需技能 | Git、YAML、`pac` CLI、PowerShell | 会用浏览器即可 |
| 人员离职风险 | 低（源码在仓库，新人可接手） | **高**（无源码，环境即全部资产） |
| 误删风险 | 低（可从仓库重建） | **高**（误删列会连带丢数据，且无备份可还原定义） |

### 一句话选型建议

- **选本方案**：维护人员不熟悉 Git / 命令行；或本项目规模小、变更不频繁；或只是想快速把流程跑起来验证价值。
- **选旧方案**：需要多人协作、需要变更可追溯、需要定期回归部署；或这套平台未来要承接多工厂推广（届时"环境即源头"会变成灾难）。
- **可以混用**：先按本手册手工搭建、验证业务闭环，业务跑通后再按旧方案把 DEV 环境里的成果导出为解决方案源码、纳入 Git 管理。**这条路是可行的**，也是风险最低的过渡方式（见 `09-发布迁移与备份手册.md` 第 6 章）。

## 最重要的代价，请务必先读

旧方案里有一句话：

> ❌ **不要先在开发环境手工建表再从环境倒扒源码。** 组件应在解决方案工程内创作，DEV 环境是部署产物而非源头。

本方案**恰恰相反**：

> ✅ **DEV 环境就是唯一源头。** 所有表、列、流程、应用都直接在门户里建，仓库里不保存任何工程源码。

这不是笔误，而是这个选择的本质代价。它带来三个必须正视的后果：

1. **没有变更历史**。三个月后没人知道某个列是谁、什么时候、为什么加的。
2. **没有自动回滚**。发错了只能手工改回去，且**托管解决方案升级不会删除旧组件**——删掉的列在目标环境会残留。
3. **环境即资产**。误删一个列会连带丢数据；租户层面的误操作没有还原点。

**缓解手段（本方案强制要求，写在 `09` 与 `10` 两本手册里）**：

| 手段 | 频率 | 说明 |
|---|---|---|
| 导出解决方案 zip 归档 | 每次发布后 | **托管版 + 非托管版各导一份**，存到受控位置，保留至少 12 个月 |
| 开启 Dataverse 审计 | 一次性配置 | 记录谁在什么时候改了哪条数据、哪个字段 |
| 用解决方案 `See history` | 每次变更后 | 查看解决方案的导入/导出记录 |
| 发布前截图留证 | 每次发布前 | 表结构、列清单、流程定义各截图存档 |
| 双人核对 | 每次发布前 | 一人操作、一人核对，避免手滑 |

## 本方案的"不用代码"边界

有一个贯穿全套文档的定义，避免后续争论：

### ✅ 允许

| 项 | 说明 |
|---|---|
| 门户界面配置 | `make.powerapps.com`、`admin.powerplatform.microsoft.com`、`flow.microsoft.com`、`make.powerautomate.com` |
| Databricks Notebook | 在浏览器里写，属于分析工作，不属于"工程化" |
| Power BI DAX | 度量值公式，在界面里写 |
| Power Query M | 由图形化操作自动生成，不手写 |
| 自适应卡片 JSON | 粘贴到 Teams 操作的文本框里 |
| Power Automate Desktop | 桌面流，图形化录制/配置 |

### ❌ 禁止

| 项 | 说明 |
|---|---|
| `pac` CLI | 包括 `pac solution`、`pac admin` 全部子命令 |
| PowerShell / PnP PowerShell | 包括 `export-dev-solution.ps1`、`smoke-test.ps1` 等 |
| `.cdsproj` / 解决方案源码工程 | 不在本地创建解决方案工程 |
| GitHub Actions / 任何 CI-CD | 不建流水线 |
| 服务主体（Service Principal） | 不需要，全部用手工账号 |
| 自研设备端采集器 | 用 Power Automate Desktop 替代 |

**为什么这么划**：这条线的本质是"**是否存在需要维护的工程源码**"。Databricks Notebook 和 DAX 是分析资产、由使用者本人维护；而 CI/CD 流水线和 CLI 脚本是基础设施代码，需要专人维护、会随平台升级失效。本方案要避免的是后者。
