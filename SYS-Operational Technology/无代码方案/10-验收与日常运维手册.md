# 10 验收与日常运维手册

> **本手册解决"怎么验收"和"上线之后每天/每周要做什么"。**
>
> **执行阶段：S8（验收）+ 上线后长期。**
>
> ⚠️ **本手册的定位是"给运维人员的操作手册"**：
> **不是"讲原理"，而是"今天该做什么、点哪里、看到什么算正常、不正常怎么办"。**

---

## 0. 开始前必读

### 0.1 本手册解决什么

| # | 问题 | 章节 |
|---|---|---|
| 1 | 怎么验收（谁签字、验什么） | §1–§3 |
| 2 | ⚠️ **每天要做什么** | §4 |
| 3 | ⚠️ **每周要做什么** | §5 |
| 4 | 每月要做什么 | §6 |
| 5 | 常见故障怎么处理 | §7 |
| 6 | 人员变动怎么交接 | §8 |
| 7 | ⚠️ **什么东西的改动会"牵一发而动全身"** | §9 |
| 8 | 运维台账要记什么 | §10 |

### 0.2 ⚠️ 本方案运维的三个特点

| # | 特点 | 含义 |
|---|---|---|
| **1** | ⚠️ **失败大多是"静默的"** | **流程挂了不报错，只是不发通知；刷新失败了页面还在显示旧数据。** → **所以"主动巡检"比"等报错"重要** |
| **2** | ⚠️ **一半的东西不随解决方案走** | **Forms / PAD / Power BI / Databricks / SharePoint / Teams**（`09` §6.1） → **运维台账是刚需** |
| **3** | ⚠️ **改一处可能要改多处** | **升选项集要改 Silver 映射；改列名要改 Power BI；改环境变量要重启流程**（`05` §1.5 / `07` §11） |

> ⚠️ **第 1 条最值得强调**：
> **代码版方案里"流程挂了"会有流水线报错、有告警邮件。**
> **本方案里"流程挂了"可能一周都没人发现。**
> **→ 所以 §4 的"每日 5 分钟巡检"是本手册最有价值的部分。**

### 0.3 一个"健康日报"的兜底

**`05` §9 的立场是"接受不做自动告警"，但建议建一个"健康日报"流程**（每天 08:30）。
**本手册把它列为 §4 的必做项之一。**

> ⚠️ **若"健康日报"流程还没建，那 §4 的巡检就更是必须人工做。**

### 0.4 执行顺序（上线节奏）

```
第 1 天    §1 验收准备 → §3 手工 UAT
第 2 天    §3 专项验证（状态机 / SLA / 权限 / 大文件 / 报表）
第 3 天    验收签署（§2）
第 4 天起  §4 每日巡检
每周一     §5 每周巡检
每月 1 日  §6 每月事项
```

| **7** | **6 个报表页面已建** | `08` §10 |
| **8** | **迁移与备份已做** | `09` §10 |

> ⚠️ **⚠️ 8 项必须"全绿"才能开始验收。**
> **若某项是黄的（部分完成），必须在 §2 的验收表里明确写"该项未通过"** ——
> **不要"因为它快好了就算通过"。** **这是验收最容易失守的地方。**

### 1.2 ⚠️ 验收环境的选择

| 选项 | 评价 |
|---|---|
| **A（推荐）：在 TEST/UAT 环境验收** | ✅ **与设计稿 §9.1 一致**；不污染生产 |
| **B：在 PROD 验收** | ⚠️ **会留下测试数据 → 编号跳号 → 业务方会疑惑** |

> ⚠️ **若选 A，验收后要"重新走一次迁移到 PROD"**（`09` §5.9）。
> **→ 所以验收期间发现的问题，改在 DEV，再迁移一次。** **这是正常的循环。**

### 1.3 参与验收的人

| 角色 | 验什么 | 是否有签字权 |
|---|---|---|
| **业务方代表** | 流程是否好用、是否符合实际 | ✅ **必须签** |
| **运维负责人** | 平台是否可运维 | ✅ **必须签** |
| **一线操作员（Operator）** | 日常操作是否顺畅 | ⚠️ **建议参与，签字可选** |
| **开发（Developer）** | 字段是否够用 | ⚠️ **建议参与** |
| **IT/安全** | 敏感字段、审计、许可 | ⚠️ **建议参与**（**特别是 `07` §8 的敏感字段决策**） |

> ⚠️ **⚠️ 一定要有"一线操作员"参与。**
> **设计者觉得"这个流程很顺"，一线操作员可能觉得"要填 24 个字段太慢"。**
> **→ 而这类问题只有在真实使用中才会暴露。**

## 3. 手工 UAT 主流程

### 3.1 主流程（9 步）

```
Forms 提交 → Teams 卡片 → 操作员改 Assigned 并分派 → 请求人看到同一记录
→ 上传图片 → 开发填根因 → 运维改 Monitoring → 请求人确认 → Closed
```

| 步骤 | 操作 | 预期 | 结果 | 证据 | 执行人 | 日期 |
|---|---|---|---|---|---|---|
| **1** | 请求人通过 Forms 提交问题 | 提交成功，收到确认 | ☐ | | | |
| **2** | 检查 Teams `01-新问题受理` 频道 | **出现 Adaptive Card，含编号、标题、严重度、深链** | ☐ | | | |
| **3** | Operator 打开记录，改为 `Assigned` 并指定负责人 | **状态流转成功；负责人收到通知** | ☐ | | | |
| **4** | 请求人打开同一记录 URL | **能看到同一条记录、同样的数据**（⚠️ **见 §3.3 的 P4 陷阱**） | ☐ | | | |
| **5** | 上传现场图片 | `IssueEvidence` 出现文件，**元数据齐全** | ☐ | | | |
| **6** | Developer 填写根因与解决方案 | 字段保存成功 | ☐ | | | |
| **7** | Operator 改为 `Monitoring` | **请求人收到确认请求**（FL-05） | ☐ | | | |
| **8** | 请求人确认 | **状态变为 `Closed`**；`bjops_issuehistory` 有新行 | ☐ | | | |
| **9** | 检查时间线 | **上述每次变更均有历史记录** | ☐ | | | |

### 3.2 ⚠️ 第 4 步为什么最容易失败

**`uat-phase1.md` §5.3 的原话**：
> **P4 是易错项。若 FL-01 未把 `ownerid` 设为 `bjops_reporter`，Requester 会看不到自己提交的问题 —— 这会导致用户完全放弃平台。**

> ⚠️ **⚠️ 这是一条"能让整个项目失败"的风险**：
> **用户提交了问题 → 想看看进展 → 打不开 → 于是继续用微信群。**
> **→ 一旦形成这个习惯，平台就死了。**
>
> **→ 所以第 4 步必须是验收的"一票否决项"**（**不过就整体不通过**）。

### 3.4 §3 自检

## 4. 每日巡检（5 分钟）

> ⚠️ **这是本手册最重要的一节。**
> **因为本方案的失败是"静默的"，所以需要"主动看"。**

### 4.1 每日 5 项

| # | 看什么 | 在哪里看 | 正常 | 不正常怎么办 |
|---|---|---|---|---|
| **1** | ⚠️ **流程运行失败** | Power Automate → **流 → 28 天运行历史 → 筛选"失败"** | **0 条失败** | §7.2 |
| **2** | ⚠️ **健康日报**（若已建） | Teams `管理员通知` 频道 | **有今日日报** | ⚠️ **没有日报 = 日报流程也挂了** → §7.2 |
| **3** | **待处理新问题** | 模型驱动应用的"待分派"视图 | **无超过 4 小时未分派的** | 手工催办 |
| **4** | ⚠️ **超期问题** | 报表"管理总览"或应用的"超期"视图 | **无新增超期** | 按 SLA 升级 |
| **5** | ⚠️ **Power BI 数据新鲜度** | 报表右上角"数据更新于" | **≤ 上次刷新 + 4 小时** | §7.3 |

> ⚠️ **⚠️ 第 1 项的做法**：
> **Power Automate 的"运行历史"里可以按"状态 = 失败"筛选。**
> **⚠️ 但要注意：这里的"失败"包括"故意失败"**（**`05` §3.9 的错误处理用 `Terminate with Succeeded`，所以那些不显示为失败**）。
> **→ 若看到失败，先看是不是"预期的失败"。**

> ⚠️ **第 5 项是"报表的数字是不是旧的"的唯一检测点。**
> **→ 若把这一项漏掉，可能出现"业务方拿了两周前的数字开会"。** **（这个场景真实发生过很多次。）**

### 4.2 ⚠️ 一个"标志位卡住"的专门检查（本方案特有）

**`05` §4.7 和 §8 指出**：**防循环用的标志位列若"卡住"，会导致通知静默失效。**

**`05` §8 建议建了一个视图：`⚠️ 自动化异常 - 标志位卡住`。**

| 检查 | 做法 |
|---|---|
| **1** | 每天打开这个视图 |
| **2** | **看有没有记录** |
| **3** | **有 → 看是哪一列卡住了 → 手工清空** |

> ⚠️ **⚠️ 为什么这是"必须每天看"**：
> **标志位卡住 → 那个问题后续的所有状态变更都不发通知 → 而流程本身不报错。**
> **→ 除非有人主动看这个视图，否则永远不会发现。**
> **→ 这正是 §0.2 第 1 条"静默失败"的典型例子。**

## 7. 常见故障处理

### 7.1 先看这张表

| 现象 | 最可能的原因 | 处理 |
|---|---|---|
| ⚠️ **"没收到通知"** | **流程挂了 / 标志位卡住 / 连接过期** | §7.2 |
| ⚠️ **"报表数字是旧的"** | **刷新失败 / 刷新配额用完** | §7.3 |
| ⚠️ **"报表打不开"** | **许可 / 成员未加 / App 未更新** | §7.4 |
| ⚠️ **"提交表单没反应"** | **FL-01 挂了 / Form Id 错了** | §7.5 |
| ⚠️ **"图片/日志上传了但看不到"** | **FL-07 挂了 / SharePoint 权限** | §7.6 |
| ⚠️ **"数字与台账不一致"** | **口径 / 时区 / 状态值 / 状态映射** | §7.7 |
| ⚠️ **"系统很慢"** | **Databricks Warehouse 太小 / 报表模型太大** | §7.8 |
| ⚠️ **"成本超预期"** | **Warehouse 没自动停 / 用了 DirectQuery** | §7.9 |

### 7.2 "没收到通知"

| 排查顺序 | 检查 | 处理 |
|---|---|---|
| **1** | **流程的运行历史** | 有失败 → 看错误详情；无失败 → 下一步 |
| **2** | ⚠️ **"标志位卡住"视图**（`05` §8） | 有记录 → 手工清空标志位 |
| **3** | **连接是否过期** | Power Automate → 连接 → 看是否有"失效"标记 → 重新授权 |
| **4** | ⚠️ **环境变量是否被改**（团队/频道 ID） | 核对 `05` §11.2 的表 |
| **5** | **Teams 频道是否被删/改名** | 重建并更新变量 + 手工重选动作里的团队/频道 |
| **6** | **流程是否被停用** | 开启 |
| **7** | ⚠️ **流程拥有者的账号是否可用** | 换拥有者并重测 |

> ⚠️ **⚠️ 第 7 项的处理要小心**：
> **换拥有者时要"重新授权连接"**（因为连接属拥有者）。
> **→ 换完必须实测一遍。**

### 7.3 "报表数字是旧的"

| 排查顺序 | 检查 | 处理 |
|---|---|---|
| **1** | **报表右上角"数据更新于"** | 若很久以前 → 下一步 |
| **2** | **Power BI 工作区 → 数据集 → 刷新历史** | 看失败原因 |
| **3** | **若"凭据无效"** | ⚠️ **PAT 过期 → 改用 AAD 或换新令牌**（`08` §2.2） |
| **4** | **若"找不到表/列"** | ⚠️ **Dataverse 或 Gold 层改了列名** → 同步改 Power Query 步骤 |
| **5** | **若"超出刷新配额"** | 减少刷新次数，或升容量 |
| **6** | ⚠️ **上游 Databricks Job 是否成功** | Job 失败 → 湖里数据没更新 → 报表刷新"成功但数字没变" |

> ⚠️ **⚠️ 第 6 项是最隐蔽的**：
> **Power BI 的刷新会成功（因为它读的是"湖里现有的数据"），但湖里没有新数据。**
> **→ 现象："刷新成功，但数字没变"。**
> **→ 所以排查"数字没更新"必须**往上游看一步**（Databricks Job）。**

### 7.4 "报表打不开"

| 检查 | 处理 |
|---|---|
| **用户有许可吗**（Pro 或容量上的查看者） | 分配许可（`08` §8.2 已提示这是"最后才发现的问题"） |
| **用户在 App 的受众里吗** | 加进受众 → 更新 App |
| **是不是 RLS 把他筛空了** | 用"查看角色"测试该用户的身份 |
| **App 是不是没更新** | 在 PROD 工作区"更新 App" |

### 7.5 "提交表单没反应"

| 检查 | 处理 |
|---|---|
| **FL-01 的运行历史** | 看是否触发、是否失败 |
| ⚠️ **表单是不是被"移到别的组"或"重建"** | Form Id 变了 → 手工改触发器 |
| ⚠️ **是不是在"错误的表单"提交**（`09` §5.4 的方案 C 陷阱） | 确认表单指向正确的环境 |
| **是不是提交了但落库失败**（校验不通过） | 看 FL-01 里被 `Terminate` 的分支 |

### 7.6 "上传了但看不到"

| 检查 | 处理 |
|---|---|
| **FL-07 的运行历史** | 看是否失败 |
| ⚠️ **SharePoint 权限** | 用户对该库/文件夹有没有读权限（`06` §8） |
| ⚠️ **`bjops_filename` 与文件名的匹配** | 命名规范是否一致（`06` §3.3） |
| ⚠️ **是不是在"暂存文件夹"里没被搬走** | 看 `06` §5 的流程有没有跑完 |

### 7.7 ⚠️ "数字与台账不一致"（本方案最需要警惕的一类）

**排查顺序（按可能性排序）**：

| 顺序 | 原因 | 怎么确认 |
|---|---|---|
| **1** | ⚠️ **时区加了两次** | **对比同一个问题的"创建时间"在台账与报表里的显示**（**差 16 小时 = 加了两次；差 8 小时 = 一次都没加**） |
| **2** | ⚠️ **状态数值搞错**（**12 = Closed，13 = Reopened，14 = Rejected**） | 核对 `附录A` 的状态值表 |
| **3** | ⚠️ **选项集映射不全**（**Silver 层只映射了部分值**） | 看是否有 `NULL` 或 `未分类` |
| **4** | ⚠️ **"关闭"用了 `statusupdatetime` 而不是事件表** | 见 `08` §4.2 ② |
| **5** | **时间范围筛选的口径不同**（新增按创建时间，关闭按关闭时间） | 确认 `USERELATIONSHIP` 有没有用 |
| **6** | **数据延迟**（湖里还没有最新数据） | 看"数据更新于" |
| **7** | ⚠️ **Dataverse 的更改跟踪被关了** → 湖里数据不更新 | 检查表的更改跟踪设置（`07` §2.4） |

> ⚠️ **⚠️ 第 1 项（时区）的排查技巧**：
> **不要看"总时长"（因为总时长还会受"事件表最新一条"的影响）。**
> **→ 直接看一个具体问题的 `createdon`：**
> | 台账显示 | 报表显示 | 诊断 |
> |---|---|---|
> | 10:00 | 10:00 | ✅ 正确 |
> | 10:00 | 02:00 | ⚠️ **多减了 8 小时**（或时序上乱了） |
> | 10:00 | 18:00 | ⚠️ **加了两次** |

### 7.8 "系统很慢"

| 原因 | 处理 |
|---|---|
| **SQL Warehouse 太小** | 升规格（**成本上升，权衡**） |
| **Power BI 模型太大** | 减少导入的列/表 |
| **Power Query 步骤太多** | 把转换放到 Databricks 做（`07` §6.5 的分工原则） |
| **Dataverse 视图太复杂** | 减少计算列/筛选条件 |
| **流程里"获取多行"没分页** | ⚠️ **`05` §5.3 已要求必须分页** |

### 7.9 "成本超预期"

| 检查 | 处理 |
|---|---|
| ⚠️ **SQL Warehouse 的自动停止是否生效** | 设为 10 分钟 |
| ⚠️ **是不是用了 DirectQuery** | 改为 Import（`08` §2.3） |
| **Cluster 是不是一直开着** | 设"20 分钟后终止"（`07` §5.2） |
| **Job 的频率是不是过高** | 从"每小时"降到"每 2 小时"（⚠️ **但要注意 `07` §4.2 的 5 快照限制**） |
| **Dataverse 存储是否超容量** | 清理旧日志（⚠️ **日志包是容量杀手**，`06` §1.3） |

## 8. 人员变动与交接

### 8.1 ⚠️ 本方案最脆弱的一点

**一个人离职可能同时造成**：

| 影响 | 原因 |
|---|---|
| **所有流程停止** | **流程以"拥有者"的身份运行**（`05` §0.3） |
| **Power BI 刷新失败** | **凭据属该人**（`08` §2.2） |
| **无法发布新版本** | **该人是唯一的"管理员"** |
| **不知道环境变量是什么** | **配置只在该人的笔记里** |

> ⚠️ **⚠️ 这四项会"同时"发生，而且是"静默"的。**
> **→ 所以 §8.2 的交接清单是必需的，不是可选的。**

### 8.2 离职/换岗交接清单（8 步）

| # | 步骤 | 说明 |
|---|---|---|
| **1** | ⚠️ **列出该人拥有的所有云端流** | Power Automate → 按拥有者筛选 |
| **2** | ⚠️ **把流程的拥有者改为服务账号或接任人** | Power Automate → 流 → 详情 → 拥有者 |
| **3** | ⚠️ **重新授权所有连接**（用新拥有者的账号） | **换完必须实测** |
| **4** | **转移 Power BI 工作区的成员/管理员** | 加接任人为管理员 |
| **5** | ⚠️ **更换 Power BI 的 Databricks 凭据** | 若是个人 PAT/AAD 凭据 |
| **6** | **转移 Teams 团队的所有权** | — |
| **7** | **交付运维台账**（§10） | **包括环境变量值、备份位置、凭据到期日** |
| **8** | ⚠️ **最后一步：把该人的账号停用，然后"再测一遍"** | ⚠️ **顺序很重要 —— 停用后测试才能发现遗漏** |

> ⚠️ **⚠️ 第 8 步是本清单的精髓**：
> **很多人做完 1–7 步就以为完事了，但"有没有漏掉某个依赖该账号的东西"只有停用后才会暴露。**
> **→ 所以流程是"停用 → 测试 → 有问题再修 → 再测"。**
> **→ 账号停用后还有"回退窗口"（通常可以恢复），所以这个顺序是安全的。**

### 8.3 日常的"降低单点依赖"

| 做法 | 效果 |
|---|---|
| ⚠️ **用服务账号做流程拥有者**（而不是个人） | **从根上消除这个问题** |
| **至少两个人有"管理员"权限** | 有人能顶上 |
| **配置登记表放在共享位置**（不是个人笔记） | 不依赖个人 |
| **每月做一次"流程拥有者检查"**（§5.1 第 6 项） | 提前发现风险 |

## 9. ⚠️ ⚠️ 变更影响矩阵（改一处要改多处）

> **这一节是本手册最有"实战价值"的部分。**
> **本方案没有编译器、没有自动化测试 → "改了 A 忘了 B" 是最常见的故障原因。**

### 9.1 六类高风险变更

#### 变更 1：修改一个"全局选项集"（增加/改名/删值）

| 要同步改 | 在哪 |
|---|---|
| ⚠️ **Silver 层的映射表** | `07` §6.4 —— **否则新值在报表里显示为 `NULL` 或原样数字** |
| **状态机的合法转移表** | `05` §4.2（若是 `bjops_issuestatus`） |
| **视图的筛选条件** | `02` §11（若是状态） |
| **流程里的分支条件** | `05` §5.3（**选项集在流程里是"整数"**） |
| **Power BI 里的度量值** | `08` §4.2（**若有硬编码的数值**） |
| **`附录A` 的选项集清单** | 本方案的字段清单 |

> ⚠️ **⚠️ 若改的是 `bjops_issuestatus`（14 个值）**：
> **它被引用在四个地方**（选项集 / 状态机 / 视图筛选 / 流程分支），
> **任何一处拼写不一致都会导致"静默失败"**（`data-dictionary.md` §2.6 已警告）。
> **→ 建议：状态值一律用"整数"比较，不要用"标签字符串"比较。**

#### 变更 2：新增/改名一个列

| 要同步改 | 在哪 |
|---|---|
| **模型驱动应用的表单** | `02` / 应用设计 |
| **视图** | `02` §11 |
| **业务规则** | `02` §12 |
| **列级安全**（**若新列是敏感的**） | `03` §4 |
| ⚠️ **Databricks 的 Bronze 读取（显式 schema）** | `07` §3.3 —— ⚠️ **这是最容易忘的！** |
| ⚠️ **Silver / Gold 的转换** | `07` §6 |
| ⚠️ **Power BI 的数据模型** | `08` §2.4 / §3 |
| **报表的视觉对象** | `08` §5 |
| **字段清单** | `附录A` |

> ⚠️ **⚠️ 为什么"Bronze 的显式 schema"最容易忘**：
> **`07` §3.3 采用了"方案 B：手工指定列"的做法**（**因为是 CDM 导出的 CSV，直接探测不可靠**）。
> **→ 这带来一个后果：Dataverse 里加了一列，Bronze 的 schema 里没有，就会"静默忽略"。**
> **→ 现象："台账里填了，报表里没有"，而流程不报错。**
> **→ 所以本手册要求：每次加列后，必须同步改 Bronze 的 schema。** **（列入变更清单。）**

#### 变更 4：改 SLA 配置（`bjops_slaconfig`）

|---|---|

| ⚠️ **不需要改报表** | 但**历史数据的"是否达标"会按新配置重算** → ⚠️ **要向业务方说明** |

> ⚠️ **⚠️ 第 2 条要注意**：
> **SLA 是"用当前配置算历史数据"还是"用当时的配置算"？**
> **→ 本方案默认是"当前配置"**（因为没存"当时的 deadline"）。
> **→ 若业务要求"用当时的配置"，需要在 `bjops_issue` 上加一列 `bjops_resolutiondeadline`（固化当时的值）。**

## 11. 上线后的第一周（特别关注期）

> ⚠️ **第一周是最关键的。** **若第一周用户就放弃了，后面很难拉回来。**

| 天 | 做什么 |
|---|---|
| **D1** | 发公告（Teams `00-公告与发布`）；贴"怎么提问"的一页说明；**强调"以后所有问题都走这个入口"** |
| **D2** | **主动找 3 个用户，问他们提交时的困难**（⚠️ **不要等他们来问**） |
| **D3** | 看提交量；**若少于预期，去问为什么**（通常是"不知道怎么用"） |
| **D4** | 检查 §7.7 的"数字一致性"（**第一次月底前一定要对一次**） |
| **D5** | 与业务方做一次 15 分钟的复盘：**哪里卡？口径对不对？** |
| **D7** | 形成一份"第一周问题清单"，逐项定处理计划 |

> ⚠️ **⚠️ 最关键的一件事**：
> **"以后所有问题都走这个入口"这句话必须由"业务方的负责人"说，而不是 IT 说。**
> **→ 若允许"继续用微信群提问题"，平台一定没人用。** **（这是本项目最大的落地风险。）**
